# Corewright: repository rules

Read `E:/Development/AGENTS.md` and `E:/Development/general-agent-rules.md` first; this file adds the local rules. Codex: `AGENTS.md` here points to this file.

- Always write `E:` paths; `D:` is the same drive (details in the shared `AGENTS.md`).
- Branch limit: an active branch has a commit in the last 24 hours; up to 10 active branches normal, 11 to 20 only with a recorded reason, 20 hard maximum.

## What this is

A Windows process manager in the spirit of Process Lasso, with a much stronger rule engine and a local HTTP API that other applications integrate with. A SYSTEM Windows service applies per-process CPU priority, affinity, I/O priority, GPU priority, memory priority, efficiency mode (EcoQoS) and memory caps from rules; a tray app and a WebView2 dashboard manage it.

## Hard constraints (owner, 2026-11-02)

**The app itself must be high-performance: a very low memory footprint and practically zero CPU usage.** These are hard constraints, not goals. Every change is judged against them; a feature that cannot meet them is redesigned or dropped.

Working budgets (proposed 2026-11-02 to make the constraint checkable; the owner may tighten them):

| Process | When | CPU | Memory (private working set) |
|---|---|---|---|
| Service | idle, dashboard closed | ≤ 0.1 % of total CPU averaged over 60 s; at most one wake-up per 2 s | ≤ 30 MB (NativeAOT publish) |
| Service | dashboard open | ≤ 0.5 % of total CPU | ≤ 40 MB |
| Tray | always | 0 % idle (event-driven, one-shot checks only) | ≤ 10 MB (NativeAOT publish) |
| Dashboard | only while its window is open | suspended and polling stopped when minimized | exits completely on close |

Design rules that follow from this:

- **No polling where an event exists.** The tray uses `SetWinEventHook` and WTS session notifications. Its only timers are one-shot foreground recheck (3 s) and presence checks (10 minutes since input); an idle presence check stops until another foreground event. No periodic polling. The service has exactly one loop (the sampler tick): 1 s while an API client is active, 2 s otherwise. ETW process start events (next phase) replace the 2 s new-process detection, not add to it.
- **No steady-state allocations per tick.** Reuse buffers, lists and dictionaries; allocate only for new processes, events and API responses. Process names and paths are read once per process lifetime.
- **Cheap rule evaluation.** Rules that only use static fields (name, path, parent, pid, session) are evaluated once per process and cached; only dynamic rules run every tick, and a rule whose slots are already claimed is not evaluated at all.
- **NativeAOT-compatible code** in Core, Service and Tray: System.Text.Json source generation only (no reflection serialization), `LibraryImport` instead of `DllImport`, no `Expression.Compile`, no runtime code generation. Workstation, non-concurrent GC with `ConserveMemory`; invariant globalization (not in the dashboard: WinForms needs the keyboard layout's culture, 2026-11-02 crash on a German PC).
- **No heavy dependencies.** Each new package (NuGet or npm) needs a reason that outweighs its memory, CPU and bundle cost. The UI has three runtime dependencies (React, TanStack Virtual, uPlot); keep it that way unless there is a clear need.
- **The UI only costs while visible:** it stops polling when `document.hidden`, the dashboard suspends WebView2 when minimized, and closing the window ends the process.
- Measure before claiming a budget is met: record private working set and CPU time of the published binaries over a fixed idle window, and state the build and the numbers. Source review is not a performance measurement.

## Game mode and CPU topology (owner, 2026-11-02)

- **Game detection** is a built-in system signal. Rules can say "while a game runs, every other process goes to low priority", "the game gets high priority", or "everything else moves to CCD1 and the game stays on CCD0". Signals, cheapest first, evaluated only on foreground change: a user list of games; Windows' own game list (`HKCU\System\GameConfigStore\Children`, `MatchedExeFullPath`); launcher library paths (Steam `steamapps\common`, Epic, GOG, `XboxGames`); full-screen or borderless foreground window (`SHQueryUserNotificationState`, window rect equals monitor rect). The service exposes it as rule fields (`isGame`) and built-in facts (`game.active`, `game.name`, `game.pid`).
- **CCD awareness:** CCDs come from the L3 cache groups (`GetLogicalProcessorInformationEx`, `RelationCache` level 3); the larger L3 marks the V-Cache CCD on X3D parts. Affinity tokens: `ccd0`, `ccd1`, `vcache-ccd`, `frequency-ccd`, `game-ccd`, `non-game-ccd`.
- **Strongest cores like Ryzen Master:** rank logical processors by the CPPC "Maximum performance percentage" in Kernel-Processor-Power event 55 (read once at start; confirmed on the owner's Ryzen 9 9950X3D2: values 131 to 135), with the hybrid `EfficiencyClass` as fallback. Affinity tokens: `best-cores:<n>`, `best-ccd`.

## Integration API (owner, 2026-11-02)

**A normal local HTTP API only: no command-line interface, no named pipes.** Kestrel listens on `127.0.0.1` only (default port 47830, `appsettings.json`). Every `/api` call needs `Authorization: Bearer <token>`; the service generates a new token at every start and writes it with the URL to `endpoint.json` in its data directory (console mode: `%LOCALAPPDATA%\Corewright`, service mode: `%ProgramData%\Corewright`). Requests whose `Host` is not loopback are rejected (DNS rebinding). The dashboard UI uses the same API as third-party connectors; never add a private side channel for it. Never print or log the token.

Autopilot v3 adds `/autopilot/preview`, `/autopilot/placements`, `/autopilot/background`; status includes mode, placed count and cap state. Settings validate numeric fields individually and return placement warnings. Foreground reports accept optional `sessionId` and `present`; caller identity comes from TCP ownership.

Endpoints (all under `/api/v1`): `status`, `system` (with history and responsiveness, PM-51), `processes`, `processes/{pid}/explain`, `rules` (GET/PUT, PUT validates and rejects on any error), `rules/validate`, `engine/pause`, `engine/resume`, `facts` and `facts/{key}` (connectors push context such as `obs.recording=true`; rules read it with the `fact` field), `session/foreground` (the tray reports the foreground process because a service in session 0 cannot see it), `events?after=<seq>`, `api-calls` (owner, 2026-11-02: the last 100 PUT/POST/DELETE calls and every 401/421 rejection, newest first, with the calling process from the TCP owner table; reads and tray foreground reports are not logged; bodies and tokens are never stored; Integrations → Recent API calls).

**Process groups (PM-39, owner decision 2026-11-02: generic, "not an island solution for only one use-case").** `PUT/GET/DELETE /api/v1/groups/{id}`, `GET /api/v1/groups`: another tool registers exact process trees (`roots: [{pid, creationTime}]`, FILETIME UTC ticks, `includeDescendants`, `ttlSeconds` 5-3600, renewed by PUT with the same id) and optionally `actions` in the rule actions schema; affinity also takes `exclusive:N` (N whole cores reserved for the group, strongest first outside the game CCD, fixed for its life, never used by Autopilot placements). `freezeAutopilot` freezes Autopilot while the group lives (fact `autopilot.frozen`). Group settings compile to rule `group-<id>` at priority 100; grouped processes are left alone by Autopilot and by user rules unless they name `group`/`groupId`. PUT applies synchronously before answering. Errors carry a stable `error`: `root-not-found` 404, `placement-unavailable` 409, `engine-paused` / `cannot-control` / `pending` / `stopping` 503 (the group is not kept; `pending` = a requested network setting is still waiting for an earlier cleanup, retry in a minute), `invalid` 400, `unknown-group` 404. No tool-specific vocabulary in this API.

## Usage history (PM-45, owner 2026-11-05)

"I then can see, okay, this antivirus is taking up half of my CPU for the whole day." `UsageHistory` adds up, per program identity and UTC hour, the exact CPU-time and I/O deltas the sampler already reads (`ProcessInfo.CpuDelta`/`IoDelta`, `GetSystemTimes` deltas for available/busy CPU time), plus private-memory MB·s and peak; no extra system calls, no steady-state allocation (accumulator cached on the process, re-looked-up only per hour). Ticks with gaps over 30 s (sleep) are not measured time. Finished hours append to `usage\yyyy-MM-dd.jsonl` idempotently (an hour already in the file is skipped; a torn tail gets a fresh line first). `usage\current.json` holds the unfinished hour with every program (unfiltered) plus finished hours not yet written (bounded to 72, kept while the disk refuses them); it is written every 5 minutes, at each hour change and at shutdown, and the hour resumes after a restart within it. The folder (day files plus checkpoint) never exceeds `settings.usage.maxStorageMb` (default 64, 8–1024; a PUT without `usage` keeps the stored value): oldest days go first, then the oldest hours of the last day. Queries stream the files and keep only per-program sums and one point per hour. Programs below 1 CPU-s, 16 MB I/O and 64 MB average memory in an hour count only in the totals ("Everything else", which also holds interrupts and unsampled short processes). `GET /api/v1/usage?from=&to=&program=&limit=` (Unix ms, default last 24 h) reads files outside `Monitor.Sync`; `DELETE /api/v1/usage` clears. UI: History page.

## Windows services (PM-46, owner 2026-11-05)

"Most services run under the same executable … only set the priorities for this service." `IdentityProbe.Services` keeps one `EnumServicesStatusEx` snapshot (Win32 and per-user services, active); attempts are throttled to one a second, and a snapshot only answers for processes created before it (PID reuse). It is consulted only for processes whose parent is `services.exe` or that are `svchost.exe` (`ServiceCandidate`), so ordinary processes never cause an enumeration and the start costs one. `ServiceTracker` (before the classifier) retries a candidate without services in fresh snapshots until five snapshots say none, re-runs identity when a list changes, and refreshes every candidate whenever a new snapshot exists (no polling: a service joining or leaving a shared host is seen when the next service starts); `ServicesVersion` changes reset the engine's static cache, so rules re-evaluate and revert normally. `ProcessInfo.Services` (key and display name, sorted by key; per-user instance suffixes `_<LUID>` stripped) is set with `Program`, so the engine's static cache resets with it. Rule field `service` (static) matches any hosted service by key or display name; `ne` means none matches. `/processes` rows carry `services`. Context-menu quick rules on a service process are `quick~svc~<first service, lower case, other UTF-16 units as _xxxx>` (lossless, disjoint from exe quick ids) with `service eq <name>` at priority 61, so they beat an older exe-wide quick rule (60). Network slots are per executable path in Windows (WFP, QoS), so the menu does not offer them per service. Priorities are per process: a host shared by several services (still common for core groups such as DcomLaunch) changes all of them; the UI says so. Moving a service into its own process (`sc config <svc> type= own`) is a persistent system change and needs an owner decision.

## Controlled resources

`GET /api/v1/devices` returns `inventoryAt` (Unix ms), `sampling`, and `devices` (disks, GPUs and interfaces).
`?history=disk:1` adds up to 300 active-client samples to that device; comma-separated IDs and `*` are supported.
Disk IDs are Windows physical indices, GPU IDs are full LUID plus physical index, network IDs are interface LUIDs; IDs can change after reboot/replacement.
History has Unix-ms `time`, `primary` (disk read B/s, GPU %, network receive B/s), `secondary` (disk write/network send B/s). Missing samples are null. It resets after an inactive period.
Loopback/filter/end-point pseudo interfaces are hidden unless `includeHidden=true`. Ordinary virtual adapters remain visible and labelled.
CM_Register_Notification watches disk, volume, display-adapter and network-interface classes, marking inventory dirty without polling. Inventory is enumerated lazily while an API client is active, initially and after a notification; failed enumeration retries are bounded to once a minute. The existing GetIfTable2 sampler reconciles dirty network inventory. One event-signaled background worker owns disk/GPU enumeration, handles and PDH, with at most one outstanding pass and no queued probes; only cached readings are copied briefly under Monitor.Sync. API requests never wait for probing (the first response may have an empty inventory). Disk/GPU handles close after 60 s idle; no device sampling or allocation per idle tick. A stalled driver can occupy only that worker; shutdown never waits for it.
Storage health is queried at most once a minute while active. Missing fields mean not available (permissions/driver support); SATA vendor SMART is not attempted. NVMe counters are lossless decimal strings; data units are 512,000 bytes. Each physical GPU in an LDA chain has its own LUID:physical ID, PDH readings and indexed D3DKMT sensor requests. DXGI aggregate capacities are omitted for linked physical rows to avoid attributing the logical adapter total to each GPU. GPU power is % of limit, not watts; engine clock is node 0; ambiguous zero sensors are unavailable.

| Slot | Mechanism | Notes |
|---|---|---|
| `cpuPriority` | `SetPriorityClass` | Realtime only with the rule's `allowRealtime`. Re-asserted up to 3 times if the process changes it back, then left alone with a drift event. |
| `affinity` | `SetProcessAffinityMask` | `all`, `p-cores`, `e-cores` (from CPU Sets `EfficiencyClass`), or a list such as `0-7,16`. Processor group 0 only (≤ 64 logical processors); CPU Sets are the next step. |
| `ioPriority` | `NtSetInformationProcess(ProcessIoPriority)` | veryLow, low, normal, high. |
| `gpuPriority` | `D3DKMTSetProcessSchedulingPriorityClass` (gdi32) | Effect depends on the driver and hardware-accelerated GPU scheduling. Realtime only with `allowRealtime`. |
| `memoryPriority` | `SetProcessInformation(ProcessMemoryPriority)` | veryLow to normal. |
| `efficiencyMode` | `SetProcessInformation(ProcessPowerThrottling)` | EcoQoS on or off; restore gives control back to Windows. |

Child processes started later join the job and get the same per-process cap. A process cannot leave a job, so revert removes the limit and keeps the empty job. New jobs have data-folder/process-identity-scoped names and one non-inheritable query-only keeper in the controlled process, permitting journal recovery after controller exit. |

Network enforcement needs administrator rights. Claims are per process identity; Windows applies them by executable path: any block, lowest nonzero upload cap, highest DSCP number. The last claim's release removes the policy/filter. Startup removes leftover `Corewright-*` ActiveStore policies after a crash; other policies are untouched. Download shaping needs a kernel driver and remains out of scope without the owner.

Per-process `netSend`/`netReceive` (bytes/s) are requested with `/processes?include=net`. Direct kernel-network ETW runs for network clients (60 s grace) OR enabled compiled `netMBps` conditions (owner, 2026-11-02); rule demand is cached at compile time. Missing data disables the entire dependent rule, including negated conditions, and Explain reports why. ETW events aggregate into a preallocated PID dictionary without per-event allocations. Elevated ETW cost still needs owner measurement.

## Rule engine invariants

- A rule is `when` (a condition tree of `group` nodes with `and`/`or`/`negate` and `cond` leaves `field op value`) plus `actions` (one value per slot). An empty group matches everything.
- **Per-slot resolution:** rules are ordered by origin (groups, then user, then Autopilot), then `priority` (higher first), then file order; user ids beginning `autopilot-` or `group-` are rejected; each slot goes to the highest matching rule that sets it. Different rules may own different slots of one process.
- **Revert:** the first time the engine writes a slot it reads and keeps the original value; when no rule claims the slot any more, it writes the original back. Pausing, rule changes and service shutdown revert everything the engine applied. Never leave a process modified after the engine stops owning it.
- Unchanged rule id/content hashes retain timing and static caches across rebuilds through stable indices.
- `sustainSeconds` (condition must hold this long before the rule activates) and `releaseSeconds` (must be false this long before it deactivates) prevent flapping.
- Process identity is `(pid, creation time)`; every Win32 handle is checked against the creation time before writing, so PID reuse can never hit the wrong process.
- A failed write (access denied, protected process) is reported once and not retried until the rules change or the process restarts.
- **Inheritance (v3):** affinity and inheritable CPU priorities are corrected before capturing originals, including first-tick claims. Walk live ancestors and carried provenance; retain bounded 30-second tombstones of observed exited parents. Retry failed put-backs four ticks and report exhaustion. An intermediate process never observed by the sampler cannot supply lineage; ETW remains the follow-up. The event stays "inherited from X; put back". A bounded write-ahead applied-changes journal restores originals after a crash only when creation time and current applied value still match. Shutdown always attempts affinity/priority despite restore backoff.
- **Foreground data:** foreground reports carry optional `sessionId` and `present` (default true). The service identifies the reporter through the TCP owner table and checks reporter/foreground creation times against the sampler. `EvalContext.ForegroundKnown` requires a live reporter, live foreground and presence. `sessionPresent` matches only that session and session 0. Unknown/locked/idle sessions stop learning and immediately release foreground-dependent Autopilot rules, including during freeze. The recent-foreground clock counts present time only. Background rules require age > 15 s.
- Never touch critical processes (pid 0 and 4, `csrss`, `smss`, `wininit`, `winlogon`, `services`, `lsass`, `LsaIso`, `Registry`, `Memory Compression`, `Secure System`, `dwm`, `fontdrvhost`) or the service itself; the list lives in `ProtectedProcesses.cs`.
- `rules.json` is user data: written atomically, the previous version kept as `rules.json.bak`, an unreadable file is never overwritten.

- **Isolation (PM-49, owner 2026-11-12):** affinity `isolate:N` = N threads of the program's own ("say only how many … the rule system needs to be so smart to shift everything around that this application is really alone"). The engine keeps one reservation per rule while any of its processes claims it, picked once by `AffinityPlacer.PickIsolated`: whole cores strongest first (CPPC), one CCD when they fit (the game CCD only for a game, otherwise other CCDs first), P-cores only on hybrid, never physical core 0, outside other isolations and group cores, at least two cores left outside isolations and group cores; refused when physical-core boundaries are unknown (an SMT sibling could stay shared). Odd N reserves the idle sibling too. Every other non-protected, ungrouped process loses the reserved cores (a rule's mask is narrowed; empty → all free cores; unclaimed → built-in `isolation-guard`). Guard writes are journaled like any write but emit no per-process Activity lines; `/status` `isolations` counts moved and refused processes. N ≤ logical − 2 × SMT width; < 64 logical processors only. Group `exclusive:N` picks avoid isolated cores. Guards never widen: an unclaimed process keeps its own mask minus the trim, read once per guard change (`_guardVersion`: reserved cores, the core-0 trim in force this tick, pause/resume/revert, rule changes), so a process that later moves itself onto reserved cores is not noticed until the next change. An owner that refuses its write drops the reservation for that process only; each new refusing process of the rule costs one quiet move-and-restore round and one Failed event. A live smoke on the owner's PC would move the owner's processes; verify offline with a fake actuator or on a spare machine.
- **Keep core 0 for Windows (PM-49):** `autopilot.keepCoreZeroFree` (default off). While Autopilot is On and not frozen, built-in `autopilot-windows-core` removes physical core 0 from every process except protected ones, the `WindowsShell` list (`ProcessInfo.cs`) and processes a user/group rule places; it never counts toward the placement limit. Evidence is driver-dependent (DPC/ISR load concentrates on CPU 0 on many systems); the UI says so.
- **Responsiveness and stalls (PM-51, owner 2026-11-13: "Process Lasso … shows the responsiveness of the system … detect system stalls … in such cases … activating our [core 0] feature"):** `ResponsivenessMeter` uses only what the tick already has, with no thread, timer or wake-up of its own: how late the tick's timed wait ended in unbiased interrupt time (a wait that spans sleep or standby carries no delay and resets the stall clock; over 30 s is ignored as a backstop; early wakes and group ticks carry no delay; it also includes the service's own thread-pool delays), ready threads per logical processor from the sampler's `SystemProcessInformation` thread entries, DPC+interrupt share of the busiest logical processor (`SystemProcessorPerformanceInformation`, now sampled every tick), and hard faults/s counted only at ≥ 90 % memory in use. Each maps linearly to a 0..1 stall share (delay 50→500 ms, queue 1→3 per CPU, DPC/ISR 30→80 %, faults 200→2000/s); score = 100 − worst share; the delay is the symptom: the cause is the largest named signal (interrupts, cpu, memory) once its share is ≥ 0.3, otherwise scheduling. DPC/ISR shares need ≥ 0.5 s per processor and fault rates ≥ 0.5 s of samples (early ticks keep the previous window); a failed process snapshot skips the meter. Stall: score < 50 for 1.5 s, or one wake ≥ 1 s late; ends after 5 s at ≥ 70. Activity logs start and end; facts `system.responsiveness`, `system.stall`, `system.stallCause`; `/system` and `/status` carry `responsiveness`, `/system` a 5-minute history. `autopilot.keepCoreZeroTrigger`: `always` (default, PM-49 behaviour) or `stall` = core 0 kept free while stalled with a queue or DPC/ISR share ≥ 0.3, until 5 minutes after the last such tick (paging and bare delays do not arm it; a free core does not help there); a PUT without the field keeps the stored value; `/status` `windowsCore.byStall`. `system.*` facts are written by the service every tick, like `game.*`: a connector's value for them is overwritten. Thresholds are first values from an idle desktop (owner's PC: up to 23 % DPC/ISR on CPU 1 at idle), not yet calibrated against real stalls. A stall shorter than the tick interval is seen only through the DPC/ISR share, which is cumulative.
- Quick rules: the process context menu saves "always" settings into one rule per process name (`quick-<name>`, priority 60, above imports and examples).

## Autopilot (owner, 2026-11-02)

"The game mode itself should be part of a mode … that automatically schedules Windows processes more smartly … Just like the ProBalance of Process Lasso does, only better with our own rule system in the backend." Working name **Autopilot** (owner may rename).

- Autopilot generates ordinary rules in its reserved origin tier; it never calls the actuator directly. User rules beat it for every slot, groups beat both. Explain and Activity show attribution.
- **Modes: Off / Observe / On.** New installations start in Observe. Settings v5 migrates existing enabled/disabled choices to On/Off once; older files are backed up. Observe learns and evaluates proposed Autopilot changes without applying them; user/group rules retain their normal behavior. `GET /api/v1/autopilot/preview` returns process, rule, slot, value and reason.
- One authoritative set of live game roots and descendants drives `isGame`, `game.active`, `game.name`, `game.pid` and CCD protection. Always-games count while running even with Autopilot off; Never-games wins. Exiting one root leaves other games active. Detection continues during group freeze.
- Game evidence is invalidated by settings and foreground reports (including the tray's one-shot 3-second recheck). Library matches require a graphics module. Full-screen graphics or denied module access is weak evidence requiring 10 seconds. Direct3D 9/10/11/12, DXGI, Vulkan and OpenGL count. Launcher exclusions migrate once.
- Game placement auto stays V-Cache on single V-Cache parts, otherwise fastest CCD. Missing CPPC or multiple V-Cache CCDs fall back to a valid CCD (ultimately CCD 0), not no placement. Invalid explicit placement leaves priority active and returns a settings warning.
- Foreground-dependent background, gaming-background and balance rules require `sessionPresent`; unknown reporter, absence, foreground, launcher, critical or game transitions release immediately, bypassing hysteresis and freeze. Learning and recent-focus time stop while absent. Build tools get CPU and I/O priority only, never efficiency mode, and no affinity outside games; while a game runs, `autopilot-game-builds` moves every listed build tool (launchers included, no load or age threshold, not counted toward the placement limit) to `non-game-ccd` (owner, 2026-11-08: keeping builds on the game's CCD "is somewhat stupid").
- Launchers share `isLauncher`: an editable known list, live children for Node/.NET (`dotnet.exe`)/Java/Gradle, a child started within 10 minutes, or learned launch rate. Placement and balancing skip them. Child evidence is based on sampled starts; short processes between samples remain an ETW limitation.
- Identity keys contain executable path and resolved host target/project/working directory, with version segments normalized. Failed reads retry four attempts; unknown targets and command/shell/inline hosts remain observing. Shared svchost identities enumerate hosted services once; any critical service protects the host. App roots stop at launchers; same identity and uncertain ancestry are protected as foreground-related. Unmapped ApplicationFrameHost protects packaged apps conservatively.
- Background statistics v4 retain the v3 file, migrate load bands (including 1.25 cores), persist decay time and age downtime. Peaks/percentiles derive from weighted bands; placement needs average >=0.1 core or p95 >=0.5. Service eligibility is per instance. One generic learned rule reads `backgroundVerdict`; it does not generate one rule per retained program. Explain carries the verdict reason.
- `auto-background` resolves to all cores except strongest `KeepBestCoresFree` physical cores while foreground/game is busy, the active game CCD, and exclusive group cores. All placed programs get the same loose mask; no packing, demand sizing, growth or reservations. An empty/full mask means no placement, with no exclusion fallback. CPPC absence uses RelationProcessorCore masks. `auto-game` resolves cheaply to the game CCD. `non-game-ccd` uses the entire non-game pool, declining affinity if exclusive reservations overlap.
- Gaming-background requires age >15 s and >=0.5 core sustained 5 s; release 15 s. It skips launchers and game trees. Balance defaults to >=0.7 core sustained 2 s under total CPU >=60% or foreground >=0.5 core; release 30 s. `cpuPriorityLowerOnly` preserves priorities already below the target.
- Placement limit defaults to 40; status exposes `autopilotPlaced` / `autopilotCapped`. Confirmed current Autopilot affinity only appears in `/autopilot/placements`; Observe proposals appear separately in preview.
- Statistics snapshot under Monitor.Sync and serialize/write on one background task. Loose placement and prune paths allocate no temporary buffers or LINQ results per tick. Per-logical-processor load (one `SystemProcessorPerformanceInformation` call) is sampled every tick since PM-51 (DPC/ISR share); loose placement does not require it.
- The applied journal is bounded (8192 outstanding slots, 8 MB, compacted on changes), flushed before process writes and completed on restore/exit. A pending intent retains the last confirmed applied value, so a failed later write cannot hide existing enforcement. An incomplete tail is preserved while valid preceding records are recovered; corrupt/unwritable journals decline new changes. Network slots keep their existing machine-wide journal. New memory jobs can be reopened in the same data scope after a crash, with process identity and membership checked before use; old unnamed jobs from earlier versions are not adopted.

## Monitoring data and its cost (owner requests, 2026-11-02)

- Sampler values (Task Manager "Details" memory, CPU time, I/O counters, …) come from the same `NtQuerySystemInformation` call and cost nothing extra.
- Per-process values that need a handle (current affinity and priorities, command line, user, GDI objects) are read only for columns the dashboard shows (`/processes?include=`), at most every 3 s, outside the engine lock; the cache is dropped 30 s after the last request.
- GPU (PDH "GPU Engine" / "GPU Adapter Memory") is sampled only while a client is active (per-logical-processor load every tick, PM-51); the PDH query is closed 60 s after the dashboard goes away. Network totals (`GetIfTable2`) are always sampled.
- CPU topology (CCDs from L3 groups, cores, SMT threads, V-Cache by L3 size) and the CPPC core ranking (Kernel-Processor-Power event 55, `MaximumPerformancePercent`; matches Ryzen Master's ★/• on the owner's 9950X3D2, tied cores shown as tied) are read once at start. Affinity tokens: `ccd0`…, `vcache-ccd`, `frequency-ccd`, `best-ccd`, `best-cores:N`.
- Every setting a rule can change is visible as a process column (owner: "pro tool", always shown); all Task Manager columns are available through the column chooser.

## Native Windows look (owner, 2026-11-02)

"This needs to look more native windows!" and "tray icon context menu also needs to be modern! not windows xp!" Every UI surface follows Windows 11 Fluent:

- Dashboard: system light/dark theme (`prefers-color-scheme`), the user's accent palette (the host injects `AccentPalette`; dark uses Light 2, light uses Dark 1), Windows 11 base colours with a matching title bar (`DWMWA_USE_IMMERSIVE_DARK_MODE`, `DWMWA_CAPTION_COLOR`), Segoe UI Variable type ramp, Segoe Fluent Icons, WinUI-style controls (NavigationView pane, buttons, ToggleSwitch, MenuFlyout context menus, ContentDialog). No custom brand palette in the chrome; the logo is the only brand colour.
- Tray: Common Controls v6 manifest, PerMonitorV2, theme-following dark menus (`SetPreferredAppMode`), the real icon at the system small-icon size.
- Icons: `assets/corewright.ico` (16 to 256 px; 16 to 24 px from the simplified `corewright-mark-small.svg`), rebuilt with `scripts/build-icon.ps1`.

## Process Lasso import (owner, 2026-11-02)

"So I can just write import everything." Rules → Import… previews and imports `prolasso.ini` from `C:\ProgramData\ProcessLasso\config` (or a chosen file) in one click. One rule per Lasso process pattern (id `lasso-…`, priority 30 for names, 25 for wildcard patterns); re-importing replaces the previous import and keeps the user's own rules. Wildcards match name, path and, when Lasso's `MatchOnCommandLine` is on, the command line (`commandLine` condition field, read on demand and never stored). Anything Lasso does that Corewright cannot express yet is listed as a note, never dropped silently.

## Layout and stack

- `src/Corewright.Core`: rule model, compiler, engine, slot formats; no Win32 calls, fully unit-testable.
- `src/Corewright.Service`: Kestrel minimal API, sampler (`NtQuerySystemInformation`), Win32 actuator, Windows service host. Runs as a console app for development or as the `Corewright` service.
- `src/Corewright.Tray`: NativeAOT Win32 tray (`Shell_NotifyIcon`), foreground reporting, opens the dashboard.
- `src/Corewright.Dashboard`: WinForms + WebView2 host; injects the token and loads the UI.
- `ui/`: React + TypeScript + Vite; builds into `src/Corewright.Service/wwwroot` (ignored by Git).
- No test project yet (see Tests).
- .NET 10 SDK, Node 26. Each project builds into its own `bin/` (a shared output folder broke incremental builds: MSBuild's incremental clean deleted `Corewright.Core.dll`); `scripts/publish.ps1` puts everything together in `artifacts/publish/`.

## Development loop

- Owner start: `start.bat` rebuilds (through `build.bat --no-start`) when `scripts\is-stale.ps1` finds sources newer than the published service, then starts the service elevated in a minimized console, the tray and the dashboard. `build.bat` = `scripts\stop.ps1` → `scripts\publish.ps1` → start (owner, 2026-11-02). `stop.ps1` uses each component's own exit path (dashboard event, tray `WM_CLOSE`, service API) and never kills by name; agents do not run it against the owner's instance. Tray → "Exit Corewright" stops a console-mode service through `POST /api/v1/app/shutdown` (refused for an installed service) and closes the dashboard.
- An agent's test service never uses the owner's port 47830 or data folder: set `Corewright__Port` and `Corewright__DataDirectory` for the process, and `COREWRIGHT_ENDPOINT_FILE` for the Vite dev proxy.

- Service: `dotnet watch --project src/Corewright.Service` (console mode, not elevated).
- UI: `npm run dev` in `ui/` and open `http://localhost:5173`; the Vite proxy reads `endpoint.json` and adds the token. Or start the dashboard with `COREWRIGHT_UI_URL=http://localhost:5173` for the real WebView2 window.
- Tray and dashboard: `dotnet run --project src/Corewright.Tray`.
- Smoke check: build, start the service in console mode with a timeout, call `/api/v1/status` and `/api/v1/processes`, stop the recorded PID.
- Agents never run the service elevated or install it. Non-elevated console mode can only change the agent's own processes, which is enough to test the engine end to end on a process the agent started itself (record its PID, stop only that PID). Installing the service (`scripts/install-service.ps1`, elevated) is the owner's step.
- **No load generators on the owner's PC:** proving that GPU, I/O or CPU priority changes contention needs competing load and runs on a CI runner or a spare machine, never here.

## Releases

**Standing approval (owner, 2026-11-02): "the release should auto publish, i dont need to say anything, you decide."** Corewright releases (tags, GitHub releases, the website) are published by the agents without asking each time; the agent decides when a state is ready (betas freely, stable releases only after the beta it comes from was tested). Required reviews and checks still apply. This replaces the shared "every release needs the owner's yes" rule for this repository only.

- Versions come from `Directory.Build.props` (`<Version>`); a `v<version>` tag makes `.github/workflows/release.yml` build the setup and `SHA256SUMS.txt` and publish the release (pre-release for `-beta.N` tags).
- First releases are betas (owner, 2026-11-02): 0.1.0-beta.1 = state at the installer merge, 0.1.0-beta.2 = networking.
- Update channels (Settings → Updates): Stable (GitHub `releases/latest`) or Beta (newest published release, beta or stable). Until the user picks one, the channel follows the installed version, so a beta setup updates on Beta.
- Website (`website/`, GitHub Pages, https://corewright.renner.dev, deployed by the manual "Website Pages" workflow): the download section shows the newest stable release, `/beta/` the newest beta, both read from the GitHub API in the browser. `scripts/publish.ps1` builds the UI and the NativeAOT binaries locally; it does not install or publish anything.
